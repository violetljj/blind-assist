按 [冻结协议](MEMORY_CARVE_PROTOCOL_20261116.md)（提交 1d0a0afb）运行，缓存重建 CPU 1480 s。
输出：`policy/report_mem_carve.json`、`mem_carve.log`。

运行前做了两项检查：
- 单会话检查：真值列和臂 0、1 与 `cache_mem_diag` 逐值相同，臂 3 与诊断臂相同。
- 投影自检：同一帧的点投回本帧，被清除的比例为 0%，99.9% 落在图像内；把前 2 帧的点投到当前帧，被清除的比例为 12%。

- **主判据**：追回比例 R = 0.14（会话 bootstrap 95% CI −0.18 到 0.35），低于 0.3。
  按协议判为**几何清除不够，需要语义检测（RGB）**。
- 次要报告：下限降低 16.1 个百分点（CI 8.2–25.6），但工作点误报为单帧的 1.97 倍（CI 1.55–2.56），原判据同样不满足。
- 明眼人行走者：R = 0.11，形态相同。
- 本设定只用当前一帧来清除，且视野外的点一律保留。为什么清不掉行人拖影（例如拖影落在视野外、或被遮挡），没有单独检验。

## 对路线的含义

在本设定（合成数据、GT 位姿、真值深度）下：
- 多帧记忆确实能把迟报下限从约 20% 压到 2–5%；
- 代价是行人拖影带来的误报；
- 只靠几何的清除去不掉拖影。

神谕去动态给出上限：下限 4.6%，迟报率 7.2% 时误报为 23.7 次/km。要接近这个上限，需要真实的行人分割或检测。
这就需要 SANPO 的 RGB 帧，同时也能把真值深度换成单目深度（DAV2），检验更真实的情形。
