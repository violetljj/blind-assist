# 手机热点优先与采集页排版：2026-10-13

用户要求两块硬件优先连接已配置的手机热点，随后要求实时预览与开始／停止相邻。原固件保持现有 Wi-Fi，手机关闭 Wi-Fi 后两板仍留在路由器；本轮修改共享网络层与采集页布局，不运行模型、训练或冻结评价。

## 行为

- 槽位 1 是手机热点，槽位 0 是原 Wi-Fi。开机、断线和 USB 重连先尝试热点，每次连接最多 12 秒，再回退原 Wi-Fi。
- 连着原 Wi-Fi 时每 30 秒异步、按已配置热点名称检查；发现热点便迁移。热点可见但连接失败后回退，并等待 120 秒再检查。
- 热点关闭后回退原 Wi-Fi；重开热点后再次迁移。扫描上限 5 秒，取消扫描后才开始连接；现有网络凭据、传感器数据格式和配置保留。
- 切网会结束正在采集的 TCP 段，保留中断记录；两板接入后在 App 点击“自动寻找设备”，再开始新段。

## 后续：双网络同时开启时的中断回归修复（待设备更新）

用户报告更新后更容易中断、重连，并明确主要出现在原 Wi-Fi 与手机热点同时开启时。本轮目标是修复会主动打断传输的切网逻辑及已复现的重连计时缺陷。范围为共享网络层、Atom/H3 活动传输标记与手机重连策略；计划验证量为两个固件编译、一个实际共享头的主机状态机程序及四个重连策略 JVM 用例。原始记录、既有失败与历史实机结果保留。证据目录为 `artifacts.local/evidence/capture-reconnect-fix-20261013/`。

确认的代码缺口：旧热点优先逻辑在 LAN 上发现热点后直接断开 Wi-Fi，没有检查正在预览或录制的传输。现在 Atom RGB/IMU 或 H3 CNH 客户端活动时不发起偏好扫描，已有扫描也取消；停止传输后等待完整检查间隔再迁移。开机与真实掉线后仍优先热点，USB 显式重试仍生效。Atom 相机跨任务活动计数用原子操作，并在所有退出路径释放；IMU/H3 的连接状态由各自主循环读取。

另一个已复现缺陷是旧连接关闭时排出的缓存帧会将新尝试的计时倒退，导致新连接过早再次重连。手机重连策略现在忽略倒退的接收时间更新，保留原数据排空、8 秒窗口及退避规则。新增两用例在旧实现失败，修复后四用例全通过；共享网络状态机检查通过，覆盖活动期间禁止扫描/迁移、扫描期间开始传输、空闲后迁移及活动标记不阻止真实掉线恢复。

上述代码路径与用户场景相符，但尚未读取本次现场设备日志，不能认定所有重复中断均由它们造成。构建与部署状态以下方最终记录为准；v10.19.2 和先前已刷固件不会因为修改源码而自动更新。

最终检查：Atom 与 H3 两个真实固件均编译通过，独立输出、源码指纹和二进制 SHA256 保存在本轮证据目录的两个 `*-manifest.json`；手机策略结果 `reconnect-policy-tests.xml` 为 4 tests / 0 failures / 0 errors。修改的九个文件 `git diff --check` 通过；全仓检查遇到其他任务已修改的 CURRENT_DECISION/PROJECT_STATE 的 CRLF 空白提示，未改动这些文件。本轮没有重新打包/安装 Android APK，也没有刷写固件或接触实时传感器流，因此用户设备仍需更新并验证双网络场景。
