## 项目定位

BlindAssist 是一个原生 Android Kotlin 助盲避障原型。项目目标是在普通手机上使用 CameraX 获取实时摄像头画面，通过本地 TFLite YOLO11n 模型完成目标检测，再由规则层判断障碍物方位、相对距离和风险等级，最后通过界面、语音和震动给出辅助提醒。

项目重点不是把手机 App 包装成可完全替代人工判断的安全设备，而是验证一条可运行、可演示、可迭代的移动端本地视觉辅助链路：摄像头取流、模型推理、检测框展示、风险判断、提醒策略、真机安装和版本演进。

## 阶段一：需求调研与问题定义

建议汇报时间：3 月上旬。

本阶段主要围绕“手机端能否低成本实现助盲避障原型”展开调研。相比专用硬件方案，手机具备摄像头、计算能力、扬声器、震动马达和便携性，适合作为课程项目和小毕设的原型载体。调研过程中需要明确几个边界：第一，项目不承诺安全级避障，只做辅助提醒；第二，优先实现本地运行，减少网络依赖；第三，优先保证真机可运行，而不是停留在算法脚本或静态演示。

这一阶段形成的核心判断是：项目应以“可运行原型”为第一目标，避免一开始就引入过重的后端、云端识别、多硬件联动或复杂多模态架构。只有先把手机端摄像头、检测、提醒链路跑通，后续的体验优化和功能扩展才有可靠基础。

主要工作内容包括：

- 梳理低视力或视障用户在行走场景中可能关注的障碍物方向、距离变化和提醒方式。
- 比较云端视觉识别、本地模型推理、专用硬件传感器等路线的实现成本和展示可行性。
- 确定以 Android 原生 App 为主体，使用手机摄像头和本地推理构建第一版原型。
- 明确项目安全边界，后续文档和界面均避免把原型描述成可以完全替代人工判断的安全设备。

## 阶段二：技术方案与架构设计

建议汇报时间：3 月中旬至 3 月下旬。

本阶段重点是把前期需求转化为可落地的技术路线。最终方案采用原生 Android Kotlin 单模块项目，使用 CameraX 负责实时取流，使用 TFLite 加载 YOLO11n 模型，使用自定义 overlay 绘制检测框，并在规则层中根据目标位置、框大小和所在区域生成风险提醒。

选择 Kotlin 和原生 Android 的原因是：移动端摄像头、生命周期、权限、TTS、震动和真机安装都能直接接入系统能力，适合做可演示 App。选择 YOLO11n 是因为模型较轻，适合移动端推理；导出为 TFLite 后可以放在 assets 中离线运行，减少网络条件对演示效果的影响。

初步架构划分如下：

- `MainActivity.kt`：应用入口、权限、CameraX 预览、推理调度和主界面控制。
- `vision/`：图像预处理、TFLite YOLO 检测、输出解析和 NMS。
- `risk/`：风险区域、相对距离、方向和等级判断。
- `feedback/`：语音提醒、震动反馈和冷却控制。
- `ui/`：检测框覆盖层和界面状态展示。
- `scripts/`：模型导出、模型检查和辅助验证脚本。

本阶段的设计重点是让链路尽量清晰：摄像头帧进入模型，模型输出检测框，规则层从检测框中抽象风险，反馈层再把风险转成用户可理解的提醒。这样的分层便于后续解释工作量，也便于在答辩中展示每个模块的职责。

## 阶段三：原型搭建与模型接入

建议汇报时间：4 月上旬。

本阶段完成第一版可运行原型，对应项目早期 v0.1.0 阶段。核心目标是把“Android 真机摄像头 + 本地 YOLO11n TFLite 模型 + 检测框展示 + 基础风险提醒”跑通，形成可以安装到手机上的 APK。

主要工作内容包括：

- 搭建 Android Gradle 项目结构，完成基础 Activity、权限和 CameraX 预览。
- 导出 YOLO11n TFLite 模型，固定输入尺寸为 320×320，并验证模型输入输出形状。
- 在 Android 端加载 `yolo11n_fp16_320.tflite` 和 `coco_labels.txt`，解析模型输出。
- 实现图像预处理、候选框过滤、NMS 和检测结果映射。
- 在预览画面上绘制检测框，初步展示识别结果。
- 添加基础风险规则和单元测试，确认核心判断逻辑可验证。
- 生成并安装 debug APK，确认真机上能启动并运行检测流程。

这一阶段的阶段性成果是：项目从“方案”变成了“手机上能打开、能识别、能展示”的可运行原型。对应归档 APK 为：

```text
releases/apk/BlindAssist-v0.1.0-debug-958d5a9-rebuilt.apk
```

## 阶段四：风险规则与提醒链路完善

建议汇报时间：4 月中旬。

原型跑通后，本阶段重点转向“提醒是否稳定、是否能表达风险变化”。单纯显示检测框不足以体现助盲辅助价值，因此项目逐步加入风险稳定、相对距离分层和更清晰的交互结构。

v0.2.0 阶段加入风险提醒稳定机制。HIGH 风险可以立即提醒，MEDIUM 风险需要连续确认，已经确认的提醒在短暂丢帧时保持一小段时间，减少检测波动导致的提示抖动。这个改动让提醒逻辑更符合真实摄像头场景：模型偶尔漏检时，用户不应立刻失去提示。

v0.7.0 阶段加入相对距离分层，用 FAR、MID、NEAR、CRITICAL 区分目标距离感和紧急程度。项目没有估计真实米制距离，而是根据检测框在画面中的位置和大小推断相对接近程度。这样既符合手机单目视觉原型的能力边界，也能让提示从“有目标”升级为“目标是否值得提醒”。

v0.8.0 阶段升级界面交互，把主风险状态、控制开关和调试信息分开，让演示时更容易说明 App 的运行状态，也让用户不必被过多调试数据干扰。

代表性成果包括：

- 风险稳定器 `RiskStabilizer`。
- 相对距离分层和紧急度评分。
- 更明确的检测、语音、震动控制。
- 可折叠调试信息和更清楚的风险来源展示。
- 对风险规则和稳定逻辑的单元测试补充。

对应归档 APK 包括：

```text
releases/apk/BlindAssist-v0.7.0-debug-d948f6b-rebuilt.apk

```

## 阶段五：真机体验、无障碍与界面迭代

建议汇报时间：4 月下旬。

本阶段重点从“功能能跑”转向“真机上能看懂、能操作、能展示”。项目基于手机截图和真机体验，对相机界面、overlay 映射、控制区布局和关怀模式进行多轮优化。

v1.3.0 阶段重构实时相机界面，加入更清晰的品牌/状态区域、风险徽标、两行控制区、Care Mode 和中心参考线。这个阶段让 App 从工程原型更接近可展示产品，老师或同学打开后能更快理解当前风险、检测状态和提醒开关。

v1.4.0 阶段根据手机截图反馈收敛界面，解决预览顶部留白、overlay 与填充预览不一致、按钮过大等问题。相机预览改为更充分填充屏幕，检测框映射也跟随预览裁剪方式调整。

v1.5.0 阶段加入轻量偏好保存，语音提醒、震动提醒和 Care Mode 可以记住用户选择；但检测仍然默认开启，避免 App 再次打开时处于静默暂停识别状态。

这一阶段体现的工作量主要在移动端体验细节上：不仅要让算法链路运行，还要让界面状态、控制按钮、调试信息和低视力辅助模式形成可解释的使用流程。

## 阶段六：阶段性综合迭代与展示准备

建议汇报时间：5 月 1 日前。

本阶段将前面分散的检测、提醒、界面和调试能力整合为更适合展示的版本。目标是让 App 不仅能识别障碍，还能解释为什么提醒、提醒强度如何变化、最近一段时间运行情况如何。

v2.0.0 阶段加入 Quiet、Standard、Sensitive 三档提醒模式。不同模式调节中风险确认帧数、提醒保持时间、语音/震动冷却和震动时长，让项目可以展示“同一检测链路下的不同使用偏好”。同时更新 CameraX 分辨率选择方式，减少旧 API 依赖。

v2.5.0 阶段加入现场可测的助行会话层，把风险分析、稳定、反馈原因和最近帧摘要整理到纯 Kotlin 逻辑中。调试面板可以展示最近 30 帧摘要，方便演示“系统不仅给结果，也能回看判断过程”。

v2.6.0 阶段继续打磨显示可信度。界面区分当前帧检测目标和短暂保持的历史提醒，避免出现“当前 0 个目标但还显示旧目标”的误解；同时把紧急度数值移入调试区，让默认界面对普通用户更友好。

对应归档 APK 包括：

## 可展示的工作量总结

项目最终形成了一条完整的移动端本地视觉辅助链路，工作量可以从以下几个角度汇报：

- 移动端工程：完成 Android Kotlin 项目、CameraX 取流、权限、生命周期、真机安装和 APK 归档。
- 模型部署：完成 YOLO11n 到 TFLite 的导出、模型资产接入、输入输出检查和 Android 端解析。
- 视觉处理：完成图像预处理、检测结果过滤、NMS、坐标映射和 overlay 绘制。
- 风险判断：完成风险区域、方向判断、相对距离分层、紧急度评分和提醒稳定。
- 反馈交互：完成语音提醒、震动提醒、冷却策略、提醒档位和 Care Mode。
- 用户体验：完成相机界面多轮迭代、调试信息折叠、状态文案优化和可解释提醒展示。
- 工程验证：完成单元测试、Gradle 构建、真机安装验证、版本号管理和多版本 APK 留存。
